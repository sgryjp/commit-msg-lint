# コミットメッセージのパースとリントの設計案

## 位置づけ

この文書は、調査資料と現行実装を基に、commit-msg フックでの実用性と実装の単純さを両立させる設計案で
ある。実装済みの仕様ではない。指定された 2 モデルの 20 往復の議論を議長が整理した。合意した方針と、
実装前に利用者の判断が必要な事項を分けて記す。

主な根拠は [Git 固有のコミットメッセージ入力調
査](../research/2026-11-13-git-commit-message-input.md) である。同調査は主に Git 2.54.0 / macOS での
実測とソース読解に基づく。[commitlint のパーサー調
査](../research/2026-11-09-commitlint-parser-design.md)、[gitlint のパーサー調
査](../research/2026-11-09-gitlint-parser-design.md)、[両ツールの比
較](../research/2026-11-06-commitlint-vs-gitlint.md)も参照した。先行 2 調査の Git 互換性に関する後日
の訂正を優先する。

## 目的と境界

- Git の内部実装やバージョン固有の例外を広く再現せず、commit-msg フックで Git の編集用注記や差分に起
  因する誤拒否を減らす。
- フックが受け取るのは cleanup 前のファイルである。フックの引数だけでは `--cleanup` の実効値
  や `-v` の有無を確定できない。**最終コミットメッセージと同一の内容を検査する保証はしない。**
- コメントや scissors 行を実際には残す Git 操作では、近似によって残る内容の違反を見逃しうる。逆に、
  Git が後で空白を整理する場合でも、空白に関する違反を報告しうる。この非対称性を隠さない。
- Git 履歴の範囲検査、フックの設置・管理、Git trailer の汎用パーサー、Git cleanup の完全再現は対象外
  とする。フック自体が実行されない経路もある。
- [README の設計方針](../../README.md#design-philosophy)どおり、幅は表示幅で測る。
  推奨と必須は警告とエラーで区別する。Git 入力への対応はこの方針を置き換えない。

## 合意した設計

### 1. 入力経路とフック用の明示モード

既存の標準入力、`--edit <path>`、公開ライブラリの `lint(input, config)`、Web デモは、指定がなければ
従来どおり入力をそのまま検査する。`--edit` のパス名や `GIT_EDITOR` からフック入力を推測しない。通常
ファイルや `git log` の出力に含まれる `#` 行を暗黙に消さないためである。

CLI に明示的なフック用モードを追加する。仮の使用例は次のとおりである。

```sh
commit-msg-lint --git-hook --edit "$1"
```

`--git-hook` は「Git の最終結果を再現する」指定ではなく、以下の固定した近似を適用する指定である。
標準入力に明示指定する場合も同じ処理方針を適用できる。名前やオプションの最終的な綴りは未決とする。
フックの案内は追加モードを紹介し、既存の `--edit "$1"` が引き続き原文検査であることも説明する。

### 2. 前処理: コメントと scissors は独立

フック用モードでは、既定で次の順序で処理する。

1. 最初の scissors 行を見つけ、その行と後続を検査対象から外す。
2. 残った行のうち、コメント接頭辞で始まる行を検査対象から外す。
3. 残りの行を現行の行正規化・解析・リントに渡す。入力ファイルは変更しない。

両処理はそれぞれ無効化できるようにする。例えばコメントだけを除く選択は、`strip` かつ `-v` なしで本文
中の scissors 形の行だけがコメントとして消える場合に有用である。一方、scissors だけを切る選択は、コ
メントを残す cleanup と `-v` の組合せで有用である。二つの無効化指定はフック用モードでのみ受け付け、
それ以外では引数エラーとする。操作は個人のフックスクリプトに書ける CLI オプションを推奨し、TOML と二
重に設定しない。具体的な綴りは未決とする。

- **両方有効**: フック用モードの既定。編集用注記と差分による誤拒否を抑えるが、
  実際に残る本文を見逃しうる。
- **コメントのみ有効**: コメントだけを除く。`-v` 等の差分は検査され、誤拒否しうる。
- **scissors のみ有効**: コメントを検査し、scissors 以降だけ除く。
  切断されずに残る本文は見逃しうる。
- **両方無効**: 前処理なし。接頭辞の取得は不要で、原文の検査と同じ。

コメント判定は接頭辞文字列の**行頭からの前方一致**とする。`#` なら `#note` も対象だが、` #note` は対
象外である。複数文字の接頭辞も扱う。

scissors 行は、**正規化前**に、行頭か
ら `<接頭辞> ------------------------ >8 ------------------------` に完全一致し、LF で終わるものとす
る。先頭の空白、末尾の追加文字、CRLF、LF のない最終行は一致しない。これは Git 2.54 の観測を基に除外
範囲を狭く定めた本ツールの固定仕様であり、Git の将来の全バージョンとの一致を保証するものではない。
CRLF の scissors 行では差分が残って誤拒否しうる。

`GIT_EDITOR`、`commit.cleanup`、`commit.verbose`、翻訳されうる案内文から Git の実効処理を推定しな
い。`-m` / `-F` の既定では `#` 行がコミットに残る一方、近似の既定では除外される。例えば長さ違反
の `#` 行は見逃される。`-v` なしで scissors に見える本文を書いた場合も、その後を誤って除外しうる。こ
れらが困る場合は独立した無効化指定か原文モードを使う。

空白整理は行わない。行末空白、先頭や連続する空行を残して従来のルールに渡す。Git が後で整理する入力で
は `line-trailing-whitespace`、`section-separator`、`header-format` などが誤拒否しうる
が、`verbatim` では空白が実際に残る。リポジトリ側で警告への変更やルール無効化を選べる。`--strict` で
は警告でも終了コード 1 になる。

### 3. コメント接頭辞と Git への依存

少なくとも一方の除外処理が有効なときのみ、CLI が Git の実行文脈から接頭辞を解決し、純粋な前処理へ値
として渡す。Git がフックに渡した環境と作業ディレクトリを引き継ぎ、`--edit` のパス名からリポジトリを
推測しない。リポジトリ判定には Git 自身を使い、worktree、bare リポジトリ、`GIT_DIR` 等を単純
な `.git` 存在判定で排除しない。

- `git config --null --get-regexp '^core\.comment(char|string)$'` 相当で両別名を設定順に取得し、
  最後の値を使う。include 等の解決は Git に任せる。NUL 区切りの各項目をキーと値の区切りで分け、
  値を勝手に trim しない。
- 正常な未設定の場合のみ Git の既定 `#` を使う。空値、改行を含む値、`auto`（大文字小文字を区別しない
  ）、不正な出力、Git の起動・設定取得失敗、必要時のリポジトリ外実行は理由を示して終了コード 2 とす
  る。未設定と失敗を混同しない。
- Git が `auto` で実際に選んだ接頭辞は確実に取得できないため、推測・再現しない。エラー時は、固定の
  Git 接頭辞への変更か、前処理を使わない検査を案内する。
- 初版では接頭辞の TOML / CLI 上書きを設けない。不一致による静かな誤除外を増やさないためである。
- 両処理が無効なら、**フック前処理のための**リポジトリ確認・Git 設定取得は不要である。ただし既存 CLI
  の設定自動探索は別途 Git を起動する。Git 不在で完全に動かすには、現行仕様どおり `--config` による
  明示指定などが必要である。
- Windows の非対話的な Git 子プロセスはコンソールを表示しない。

Git 2.45 より前は複数文字の `core.commentString` などの意味が異なる。古い Git に対する完全互換は約束
しない。`git -c` の値がフックからどう見えるかは調査時点で未検証であり、実フック試験が必要である。値
を取得できても、別名の解釈や古い Git の差により実際の接頭辞と食い違う可能性は残る。

### 4. パースと位置情報

パーサーやリントの中で Git を起動しない。前処理は元の行番号を持つ検査対象行の列を作り、リントはそ
の**論理行列**を使う。除外行は列に含めないが、残った行の診断は元入力の 1 始まりの行番号で報告する。
Git の cleanup 後の行番号ではない。診断形式、ルール ID、並び順、終了コード 0 / 1 / 2
と `--strict` の意味は維持する。

- 除外後の最初の行を Header とする。先頭空行を勝手に飛ばさない。空白だけの行も従来どおり空行ではな
  い。
- 例えば Header、空行、コメント、Body の順なら、コメント除外後は空行一つの区切りである。Header、コメ
  ント、Body の順なら区切り不足を Body の元行番号で報告する。
- 全行が除外された場合は空 Header として扱い、`header-format` が有効なら元入力の 1 行目に報告する。
  メッセージでは除外後に空になったことを伝える。ルールが無効なら通常どおり診断しない。
- CRLF を LF として扱う現行のルール、末尾 LF を最大一つ除く扱い、単独 CR の制御文字診断は維持する。
  scissors 判定だけは正規化前の終端を参照する。

Header の不一致はパース自体の致命的エラーにせず、現行どおり `header-format` と、パース可能なときだけ
実行する構成要素ルールに委ねる。行単位の位置情報を保持するだけで現在の診断要件を満たせるため、先行調
査で候補となった完全なロスレス構文木や汎用パーサープリセットは導入しない。ルールが独自に生テキストを
再分割して位置を推測する設計も避ける。

既存の公開 `lint(&str, &Config)` の振る舞いを保ちながら、内部で行列を受け取る共通のリント処理に委譲
する構成を想定する。Git 設定取得は CLI の責務とし、Web デモと純粋なリント処理は Git に依存させない。
新たな公開インターフェースの要否は実装時に最小限で判断する。

### 5. Footer、Trailer、特殊な件名

初版では [現行 Footer のヒューリスティック](../message-format.md#footer-and-trailer-detection)とルー
ルを維持する。これは Git `interpret-trailers` の 25% 規則、`---`、`trailer.*` 設定を再現せず、Git
trailer の一般的な判定を保証しない。`-s` や `--trailer` でフック前に追加された行も通常の検査対象にな
る。

現行方式では本文途中の `Note: value` から Footer に移り、空行不足や Footer 幅の診断が出ることがあ
る。末尾段落に限定すると、今度は本文と `Refs: value` の間の空行欠落を見逃しうる。複数行の Trailer 値
と不正な候補の区別も必要である。Footer の変更はフック前処理と切り離して評価する。

`fixup! `、`squash! `、`amend! `、`Merge `、`Revert "` 等の特殊な件名の免除は初版では導入しない。現
行ルールによってフックが拒否しうることを明記する。全ルールの一括免除では本文の幅や制御文字まで見逃す
ため、将来対応する場合も免除範囲を限定する方向で検討する。

### 6. エンコーディングと対象外の経路

入力は従来どおり UTF-8 に限り、不正な UTF-8 は終了コード 2 とする。Git は UTF-8 以外を許す場合があ
り、`i18n.commitEncoding` を使うリポジトリではフックが失敗しうることを明記する。エンコーディング変換
は初版に含めない。

編集なしの cherry-pick、revert、rebase 等には commit-msg フックが動かない経路がある。フックを通して
いないコミットの検査は保証しない。範囲指定による履歴検査はこの CLI の機能ではない。

## 検証計画

1. **純粋な前処理・リントのテスト**: 4 通りの処理選択、単一・複数文字接頭辞、行頭以外、
   scissors の完全一致・インデント・CRLF・終端 LF なし、空入力と全行除外、コメントを挟んだ区切り、
   元行番号を確認する。テスト名に期待する振る舞いを記す。
2. **従来の回帰**: 標準入力、`--edit`、公開 `lint`、Web の結果、CRLF、Footer、表示幅、重大度、
   `--strict`、UTF-8 エラー、診断順を維持する。両処理無効時は前処理のために
   Git を呼ばないことも確認する。
3. **実 Git のフック試験**: 使い捨てリポジトリで `-m` / `-F`、エディターありの既定、`-v`、
   `strip` / `whitespace` / `scissors` / `verbatim`、複数文字接頭辞、未設定、`auto`、worktree、
   include と `git -c` の伝播を代表例として確認する。検査対象、元行番号、診断、終了コードに加え、
   意図的な最終結果との差も検証する。すべての組合せで Git と同じ結果になることは要求しない。
4. **変更検知**: Git が生成する scissors 行の形と、フック時の設定取得をカナリアとして試験する。
   Git の変更による失敗は、自動的に Git に追従するのではなく、仕様変更・リスク・
   対応要否を評価する契機とする。
5. **環境**: Git 2.45 と現行版、Linux・macOS・Windows での実行を目標にする。
   2.45 未満については上記の互換性の限界を明記する。試験環境を用意できない組合せは、
   実施済みと記さず追跡する。

## 未決事項と意思決定が必要な問い

1. **特殊な件名の許容範囲**: `fixup! `、`squash! `、`amend! ` の Header 形式・構成要素ルールだけを
   opt-in で免除するか。適用先はフックのみか全入力か。フックのみなら同じ設定でもフックと stdin / Web
   の結果が異なる。全入力なら同じ設定を CI の stdin 検査に使った場合も免除される。いずれも手書きの
   同じ接頭辞を識別できず、残りの幅・空白・制御文字・Body / Footer の検査も失敗しうる。
   Merge / Revert の許容は別途判断する。
2. **独立した操作の CLI**: 2 処理の個別無効化は合意したが、例えば `--no-strip-comments` /
   `--no-cut-scissors` と、値を指定する方式のどちらにするか、
   `--git-hook` の名称を含めて確定していない。
   共有 TOML での選択は個人の Git 設定と食い違いやすいため、CLI を推奨する。
3. **Footer の改善**: 現行の早すぎる Footer 判定と、末尾段落限定による区切り欠落・複数行値の
   見逃しのどちらを優先するか。実例と互換性を基に別途決める。
4. **Git 設定と対応範囲**: 一時 `-c` のフック内での可視性を実測し、古い Git と複数文字設定の扱い、
   サポート対象バージョンを確定する。取得が不十分な実例が見つかった場合に限り、
   接頭辞の明示 override の必要性を再評価する。
5. **UTF-8 以外**: 制限の明記だけで十分か、`i18n.commitEncoding` に基づく変換を将来追加するか。
   変換は依存関係と誤変換リスクを増やす。

## 議論の経過と調整

参加者 A は `openrouter/openai/gpt-6.1-sol`、参加者 B は `openrouter/anthropic/claude-opus-5.5`。議
長が各応答を相手に渡し、20 往復で検討した。

- **1–3 往復**: 両者とも明示フックモードと元行番号の維持を提案。B の固定 `#` 案に A が設定不一致に
  よる
  静かな見逃しを指摘し、B は Git 設定取得へ修正した。未設定と取得失敗を区別することで一致した。
- **4–6 往復**: `auto` や取得失敗時の回避策、接頭辞 override、2 処理の独立性を議論。
  B は当初コメントのみの選択を不要としたが、`strip`・`-v` なしの反例を両者が確認し、独立制御に合意し
  た。
- **7–8 往復**: scissors の CRLF を正規化後に一致させる単純さと、元入力の LF 終端まで限定する
  見逃し防止が衝突。実装負担を小さくできる条件で、B が限定判定に同意した。CRLF による誤拒否は残る。
- **9–10 往復**: Git の空白整理を模倣すると違反が消え、方式も確定できないため、整理しないことで一
  致。
  除外後の論理行による構造判定と元行番号の扱いを具体化した。
- **11–13 往復**: 特殊件名を全体免除せず、必要なら Header 関連のみ免除する方向で一致。
  ただし opt-in 免除をフックだけに適用するか全入力に適用するかは対立が残り、初版から切り離した。
- **14 往復**: Footer の現行方式と末尾段落方式の双方に誤判定があり、互換性も変わるため、
  現状維持と別途評価で一致した。
- **15–18 往復**: Git 設定の取得、リポジトリ外の扱い、`auto` 対策を再検討。途中で双方が相手案へ譲歩
  して
  立場が入れ替わったが、Git 設定が必要な場合に限りリポジトリを要求する案に統一した。
  CLI 接頭辞 override は一度候補に上がった後、静かな誤除外と複雑さを理由に初版見送りで一致した。
- **19–20 往復**: 実 Git と固定仕様のテスト、意図的な差、Git 更新のカナリアを確認。
  2 処理の選択は CLI を推奨し、綴りは未確定とした。UTF-8 制限とフック未実行経路も残る制約として整理
  した。
