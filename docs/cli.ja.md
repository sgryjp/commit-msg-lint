# CLI リファレンス

[English](cli.md) | [日本語](cli.ja.md)

英語版が正式な原文です。

```text
commit-msg-lint [OPTIONS]
```

CLI は標準入力、ファイル、単一の Git コミット、または明示的な Git コミット範囲からコミットメッセージを
読み取り、設定された Rule に照らして検査します。また、単独オプションで情報を出力します。
メッセージの変更や Git フックのインストールは行いません。

## オプション

| オプション | 説明 |
| --- | --- |
| `--edit <path>` | 標準入力の代わりにファイルからメッセージを読み取る。 |
| `--commits <revision-or-range>` | 単一のコミット、または明示的な Git 範囲で選択されたコミットを lint する。`--edit` と併用不可。 |
| `--config <path>` | 設定ファイルを探索する代わりに指定されたファイルを使用する。 |
| `--strict` | Lint Rule の警告を失敗として扱う。 |
| `--print-default-config` | 組み込みの既定値を編集可能な JSON として標準出力に出力して終了する。 |
| `--print-config-schema` | 設定の JSON Schema を標準出力に出力して終了する。 |
| `--help-for-agents` | [エージェント向けガイダンス](agent-usage.ja.md)を標準出力に出力し、正常終了する。 <!-- rumdl-disable-line MD089 --> |
| `-h`, `--help` | コマンドのヘルプを表示し、正常終了する。 |
| `-V`, `--version` | プログラム名とバージョンを標準出力に出力し、正常終了する。 |

オプションは任意の順序で指定でき、それぞれ一度だけ使用できます。`--edit` と `--commits` は相互に
排他的です。`--commits` は標準入力を無視し、`--config` と `--strict` を組み合わせることができます。
`--help-for-agents`、`--print-default-config`、`--print-config-schema` はそれぞれ単独で使用する
必要があります。これらのいずれかを `--help` や `--version` を含む別の引数と組み合わせると、終了
コード `2` の引数エラーになります。これらの単独オプションは標準入力を読まず、Git を起動せず、設定の
探索や読み込みを行わず、フィルタリング用環境変数も読み取りません。`--help-for-agents` はビルド時に
バンドルされた Markdown を出力します。`--print-default-config` は現在の設定ではなく組み込みの
既定値を出力します。`--print-config-schema` はこの CLI に一致するスキーマを出力しますが、最新の
公開スキーマとは異なる場合があります。[エディター用スキーマと互換性](configuration.ja.md#エディター用スキーマと互換性)を参照して <!-- rumdl-disable-line MD089 -->
ください。`--edit` と `--config` に渡す相対パスは現在の作業ディレクトリを基準に解決されます。

## 例

標準入力から読み取ります。

```sh
printf 'feat: add parser\n' | commit-msg-lint
```

メッセージファイルを読み取ります。設定の明示や strict モードの指定もできます。

```sh
commit-msg-lint --edit .git/COMMIT_EDITMSG
commit-msg-lint --config config/lint.jsonc --strict --edit message.txt
```

Git のリビジョンが指定するコミットだけを lint します。祖先コミットは含まれません。

```sh
commit-msg-lint --commits HEAD
commit-msg-lint --config config/lint.jsonc --strict --commits v1.2.3
```

既存の Git `commit-msg` フックでは、フックの第 1 引数を渡します。

```sh
commit-msg-lint --edit "$1"
```

保存済みコミットまたは範囲の lint については[履歴入力](#履歴入力)を参照してください。 <!-- rumdl-disable-line MD089 -->
CLI はフックをインストールせず、Git のすべてのコミット経路がフックを呼び出すわけではありません。Git は最終的な
cleanup の前にメッセージをフックに渡します。同じフックコマンドは CLI の既定の
[メッセージのフィルタリング](#メッセージのフィルタリング)でも動作します。設定方法と <!-- rumdl-disable-line MD089 -->
トラブルシューティングについては [Git フック連携ガイド](git-hooks.ja.md)を参照してください。 <!-- rumdl-disable-line MD089 -->

## 入力

lint 時に `--edit` も `--commits` も指定しない場合、CLI は標準入力を EOF まで読み取ります。
`--edit` を指定するとファイル全体を読み取り、標準入力を無視します。`--commits <revision-or-range>`
を指定すると、CLI は単一のコミット、または明示的な二点・三点範囲で選択されたコミットを読み取ります。
単一リビジョンはちょうど一つのコミットに解決され、祖先をたどりません。ブランチ、タグ、完全な
オブジェクト ID は、コミットに解決される場合に受け付けられます。不正な、利用できない、または
コミットでないリビジョンや範囲の端点は実行時エラーです。オプションインジェクションを防ぐため、`-` で
始まるリビジョン端点は拒否されます。`--commits` は `--edit` と併用できず、標準入力を読み取りません。

標準入力とファイルのメッセージは有効な UTF-8 でなければなりません。CLI は Git の
`i18n.commitEncoding` 設定に基づく変換を行いません。履歴入力では CLI は Git に UTF-8 でメッセージを
出力するよう要求し、Git が変換可能な場合は各コミットのエンコーディングヘッダーを使用します。
Git の出力が有効な UTF-8 でない場合、CLI は対象コミットを特定する実行時エラーを報告します。Git は
埋め込まれた NUL で履歴メッセージを切り詰める場合があります。[履歴入力](#履歴入力)を参照して <!-- rumdl-disable-line MD089 -->
ください。lint のために CRLF は LF に正規化され、最後の改行一つはメッセージ内容から除外されます。
標準入力とファイル入力では正規化前にフィルタリングが実行されます。特に CRLF で終わる scissors 行は、
後述のとおりマッチしません。
組み込みの既定値では、空のメッセージは `header-format` Rule に違反します。
既定では、認識された Git 生成またはホスティングサービス生成の Header 形式は、すべての Rule を黙って
通過します。マッチングの範囲、設定、および幅と重大度の検査への影響については
[無視するメッセージ](configuration.ja.md#無視するメッセージ)を参照してください。Header がマッチしても <!-- rumdl-disable-line MD089 -->
生成元の証明にはなりません。編集なしの revert や cherry-pick を含む一部の Git 操作は `commit-msg` を
呼び出さない場合があります。検査が必要なら生成されたメッセージを別途確認してください。

## 履歴入力

単一コミットおよび明示的な範囲の検査が可能です。

保存済みの Git コミットまたは範囲を検査するには `--commits` を使用します。引数はコミットに解決される
単一リビジョン、または `..` もしくは `...` で区切られた二つの明示的な端点を持つ範囲でなければ
なりません。リビジョンにはコミット ID やブランチ名・タグ名などの ref を使用できます。単一リビジョンは
そのコミットだけを選択し、祖先は選択しません。単一コミットとして解決される引数は、`..` を含んでいても
単一リビジョンとして扱われます。それ以外の場合は両端点がコミットに解決されなければなりません。有効な
端点への分割方法が複数ある場合、範囲は拒否されます。曖昧でないリビジョンまたはコミット ID を使用して
ください。二点範囲 `A..B` は `B` から到達可能で `A` からは到達できないコミットを選択します。
三点範囲 `A...B` は対称差、すなわちいずれか一方の端点から到達可能で両方からは到達できないコミットを
選択します。例を示します。

```sh
commit-msg-lint --commits HEAD
commit-msg-lint --commits v1.2.0..HEAD
commit-msg-lint --commits "$BASE_SHA...$HEAD_SHA"
```

これは Git のリビジョン選択の意味論です。選択されたコミットは逆トポロジカル順に報告されるため、
親が子孫より先になります。関連のないコミットの順序は Git が決定します。各コミット内の診断は通常どおり
行と Rule ID の順序を維持します。履歴の各診断は完全なコミットオブジェクト ID と、Git の出力した
メッセージの 1 始まりの行番号を示します。オブジェクト ID の長さはリポジトリのハッシュ形式に依存します。
診断のない正常実行では何も出力しません。lint 診断と実行時エラーは標準エラーに出力されます。

履歴 lint は、他の CLI 入力と同じ探索された設定、または `--config` で選択したファイルを使用します。
設定された Lint Rule、重大度、Display Column の測定、および無視するメッセージの方針がすべて適用されます。
`--strict` は Lint Rule の警告を失敗に昇格させますが、設定された方針で無視されたメッセージは strict
モードでもすべての Rule から除外されたままです。[設定リファレンス](configuration.ja.md)および <!-- rumdl-disable-line MD089 -->
[無視するメッセージ](configuration.ja.md#無視するメッセージ)を参照してください。 <!-- rumdl-disable-line MD089 -->

標準入力や `--edit` とは異なり、履歴入力では Git が表示用に出力するメッセージをコメント行の除去や
scissors での切断なしに検査します。フィルタリング用環境変数は読み取られず、Git のコメントプレフィックスも
解決されません。それらの変数が不正な値でも履歴検査には影響しません。CLI は `i18n.logOutputEncoding` を
上書きして、Git に UTF-8 出力を要求します。Git はメッセージ変換時にコミットのエンコーディングヘッダーを
使用しますが、変換に失敗したり、不正なバイトをそのまま残したりする場合があります。有効な UTF-8 でない
出力は、lint 診断ではなく対象コミットを特定する実行時エラーです。CLI は不正なバイトを置換しません。
有効なメッセージには、既存のフィルタリングなしのメッセージ処理と行処理が使われます。
[メッセージ形式](message-format.ja.md#入力と行)を参照してください。 <!-- rumdl-disable-line MD089 -->

履歴入力は保存されたコミットオブジェクトのバイト単位の厳密な監査ではありません。Git のメッセージ出力は
埋め込まれた NUL で止まります。NUL およびそれ以降の内容は検査も診断もされません。トレードオフについては
[決定記録](adr/0004-git-history-input.md)を参照してください。 <!-- rumdl-disable-line MD089 -->

不正な、利用できない、またはコミットでないリビジョンは空の選択結果ではなく実行時エラーです。
shallow でないリポジトリでコミットを選択しない有効な範囲は、lint 診断なしで成功します。CLI は
shallow リポジトリでは、単一コミットや空の範囲を含む履歴入力を実行時エラーとして拒否します。
リポジトリの fetch、履歴の深化、unshallow は行いません。履歴検査では集計件数を出力しません。

CI では、linter を実行する前に shallow でないチェックアウトと選択範囲に必要な履歴を取得してください。
例えば GitHub Actions では `actions/checkout` の `fetch-depth: 0` で全履歴を取得できます。linter が
自動的に取得することはありません。shallow クローンでは両端点を解決できてもコミットが欠落する場合が
あります。shallow でないリポジトリであることだけでは、必要なすべてのオブジェクトが利用できる保証には
なりません。

push では、両方のリビジョンが利用可能な場合、`"$BEFORE_SHA..$AFTER_SHA"` は新しい先端から到達可能で
古い先端からは到達できないコミットを検査します。プルリクエストでは `"$BASE_SHA..$HEAD_SHA"` は
head から到達可能で base からは到達できないコミットを検査します。イベントと検査対象のコミット集合に
合うリビジョンを選んでください。三点範囲は Git の対称差であり、すべてのホスティングサービスが表示する
コミット一覧と厳密に一致する保証ではありません。履歴 lint は選択されたコミットについて Git が出力する
メッセージを検査し、将来の squash マージのメッセージは検査しません。squash マージは独自のメッセージを
持つ新しいコミットを作成するため、そのコミットが存在してから別途検査する必要があります。

## メッセージのフィルタリング

標準入力と `--edit` では、CLI は既定でコメント行を除外し、scissors 位置で切り詰めます。入力ファイルを
書き換えることはありません。履歴入力ではこれらのフィルターを使わずに Git のメッセージ出力を検査し、
フィルタリング用環境変数の読み取りや検証も Git のコメントプレフィックスの解決も行いません。公開
`lint(input, config)` ライブラリ API と Web デモも、このフィルタリングなしで元の入力を検査します。
理由とすべての制約については[設計](design/commit-message-parsing-and-linting.md)と <!-- rumdl-disable-line MD089 -->
[決定記録](adr/0002-default-message-filtering.md)を参照してください。 <!-- rumdl-disable-line MD089 -->

| 環境変数 | 効果 | 既定値 |
| --- | --- | --- |
| `COMMIT_MSG_LINT_STRIP_COMMENTS` | コメントプレフィックスで始まる行を除外する。 | 有効 |
| `COMMIT_MSG_LINT_CUT_SCISSORS` | scissors とそれ以降の行を除外する。 | 有効 |

各変数は独立しており、指定されていない変数は有効のままです。真として受け付ける値は `1`、`true`、
`yes`、`on`、偽の値は `0`、`false`、`no`、`off` です。英字の大文字と小文字は区別しません。空の値、
先頭または末尾の空白、その他の値、および非 Unicode 値は終了コード `2` の設定エラーです。これらの制御は
JSONC 設定でも CLI オプションでもありません。

どちらかの操作が有効な場合、CLI は現在のリポジトリのコンテキストで Git を使い、`core.commentChar` と
`core.commentString` を設定順に読み取って最後の値を使用します。Git はインクルード、worktree、継承された
Git 環境変数を解決します。どちらのキーも設定されていない場合や現在のディレクトリがリポジトリ外の場合、
プレフィックスは `#` です。大文字と小文字を区別しない `auto`、空の値、改行を含む値、不正な Git 出力、
または必要な Git の起動や設定照会の失敗は終了コード `2` になります。その場合は Git で固定の
プレフィックスを使うか、両方の操作を無効にしてください。値の前後の空白は除去されず、`--edit` のパスから
推測されることもありません。両方の操作が無効な場合、プレフィックスの解決のために Git は呼び出されません。
ただし `--config` を指定しない限り、設定探索では Git が呼び出される場合があります。

継承された `GIT_CONFIG` 変数により、`git config` が `git commit` の使用するファイルと異なるファイルを
読むことがあるため、プレフィックスが異なる場合があります。リポジトリ探索時の認識できない Git トレース
出力や複数行のトレース出力も、リポジトリ外としてのフォールバックではなく設定エラーを引き起こす場合が
あります。いずれの場合も Git 環境を調整するか、両方のフィルタリング操作を無効にしてください。

scissors による切断を先に行い、次にコメントを除去します。コメント行はプレフィックスで始まる必要が
あります。プレフィックスが `#` の場合、`#note` はマッチしますが ` #note` はマッチしません。複数文字の
プレフィックスもサポートします。Git 2.45 より前のバージョンは複数文字のプレフィックスやエイリアスの
扱いが異なり、完全な互換性は保証されません。scissors 行は次の行全体に一致し、元の入力で LF で終わる
必要があります。

```text
<prefix> ------------------------ >8 ------------------------
```

インデントされた行、余分な文字がある行、CRLF で終わる行、LF のない最終行は scissors にマッチしません。
コメント除去が有効な場合、マッチしない scissors に似た行もコメントとして除去されることがありますが、
その後の内容は切断されません。通常の CRLF 行は lint のために正規化されます。CRLF の scissors 行に
対する Git for Windows の動作を含め、Windows 固有の動作は検証されていません。LF のみという条件は
この設計によって定められたもので、Git for Windows についての主張ではありません。

このフィルタリングは意図的な近似であり、Git の cleanup を再現するものではありません。特に、Git の
`-m` と `-F` に対する既定の cleanup はコメントを保持しますが、CLI の既定では除外します。また、
マッチする scissors 行があると、Git がそれを保持する場合でも lint 入力は切り詰められます。逆に、
Git が cleanup で除去する空白を linter が検査する場合もあります。内容を保持する意図がある場合、
呼び出し側は Git のオプションと lint 方針を整合させる必要があります。

完成済みメッセージを渡されたとおりに検査するには、両方の変数を使用します。

```sh
COMMIT_MSG_LINT_STRIP_COMMENTS=false \
COMMIT_MSG_LINT_CUT_SCISSORS=false \
commit-msg-lint --edit message.txt
```

エージェントが既存のフックを通して完成済みメッセージをそのままコミットするには、これらの制御と Git の
cleanup オプションを組み合わせます（POSIX シェル）。

```sh
COMMIT_MSG_LINT_STRIP_COMMENTS=false \
COMMIT_MSG_LINT_CUT_SCISSORS=false \
git -c commit.verbose=false commit --cleanup=verbatim -F message.txt
```

環境変数は linter にのみ影響します。`--cleanup=verbatim` と Git の verbose 設定の無効化は、それぞれ
別個の Git の選択です。

## 診断と終了コード

lint 診断は次の形式で標準エラーに出力されます。

```text
<source>:<line>: <severity>[<rule-id>] <message>
```

`<source>` は `<stdin>`、`--edit` に渡されたパス（非 UTF-8 のパス文字は置換）、または履歴入力での
完全なコミットオブジェクト ID です。行番号は 1 から始まり、標準入力またはファイルモードでは行が
フィルタリングされても元のメッセージを、履歴モードでは Git の出力メッセージを参照します。各メッセージの
診断は行番号、次いで Rule ID の順にソートされます。例えば組み込みの既定値で
`printf 'feat:subject\n' | commit-msg-lint` を実行すると、次が出力されます。

```text
<stdin>:1: error[header-format] header does not match the Conventional Commit format
```

診断のない正常な lint 実行では何も出力しません。警告は失敗を引き起こさない場合でも標準エラーに出力
されるため、終了コード `0` は警告がなかったことを意味しません。`--strict` は明示的に指定された場合に
のみ Lint Rule の警告を終了コード `1` に昇格させます。CLI はエージェントに strict モードを強制しません。
履歴入力では strict モードにかかわらず shallow リポジトリは実行時エラーです。診断の出力後に Git、
読み取り、デコードのエラーが発生した場合、出力済みの診断はそのまま表示され、コマンドは `2` を返します。
lint 診断とコマンドエラーは標準エラーに出力されます。

| 終了コード | 意味 |
| --- | --- |
| `0` | lint エラーなし。strict でなければ警告は許容される。情報表示オプションと shallow でないリポジトリの有効な空の範囲は成功する。 |
| `1` | 1 件以上のエラー診断、または `--strict` 指定時に Lint Rule の警告がある。 |
| `2` | 引数、設定、shallow リポジトリ、Git、一時ファイル、メッセージの読み取り、UTF-8 デコードのエラー。 |

## 設定の探索

履歴入力を含む lint 時には、`--config` でファイルを明示的に選択して探索を省略できます。それ以外の場合、
CLI は Git を実行して現在の作業ディレクトリを含むリポジトリのルートを見つけ、そこにある
`commit-msg-lint.jsonc` だけを探します。リポジトリがない場合やルートに設定ファイルがない場合、通常の
メッセージ入力では組み込みの既定値を使用しますが、履歴入力には引き続き Git リポジトリが必要です。
明示的に指定されたファイルは拡張子にかかわらず JSONC として解析されます。探索には Git を実行できる
必要があります。その他の探索失敗、読み取れないファイル、不正な設定は、既定値を使用する理由ではなく
エラーです。設定はメッセージを読む前に読み込まれます。

形式、既定値、Rule の設定については[設定リファレンス](configuration.ja.md)を参照してください。 <!-- rumdl-disable-line MD089 -->
