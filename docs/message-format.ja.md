# メッセージ形式リファレンス

[English](message-format.md) | [日本語](message-format.ja.md)

`commit-msg-lint` は UTF-8 のコミットメッセージを、Header と、それに続く任意の Body および Footer の行として検査します。
このリファレンスは Footer のヒューリスティックを含む現在の実装を説明するものであり、汎用の Conventional Commits パーサーや
Git trailer パーサーではありません。すべての設定、デフォルトの Type、Rule のデフォルト値、重要度の上書きについては
[設定リファレンス](configuration.ja.md)を参照してください。 <!-- rumdl-disable-line MD089 -->

例えば、組み込みのデフォルト設定では次のようになります。

```text
feat(parser)!: support multiple inputs

Explain the change and its motivation.

BREAKING CHANGE: callers must provide a list
Refs #123
```

## 入力と行

CLI は標準入力または `--edit` で指定したファイルから UTF-8 を読み取ります。
履歴入力では Git に表示用の UTF-8 メッセージを要求し、
それでも無効な UTF-8 である出力は入力エラーになります。Git は保存されたメッセージの NUL 以降の内容を省略することがあります。
[履歴入力](cli.ja.md#履歴入力)を参照してください。 <!-- rumdl-disable-line MD089 -->
デフォルトでは、標準入力と `--edit` の入力は、まず最初に一致する scissors 行で
切り詰められ、その後コメント行が除外されます。各操作は独立して無効にできます。履歴入力、公開ライブラリ API の
`lint(input, config)`、および Web デモは入力をフィルタリングせずに検査します。標準入力と `--edit` に対する正確な一致条件、
環境変数による制御、Git のプレフィックス解決、および制限については
[CLI リファレンス](cli.ja.md#メッセージのフィルタリング)を参照してください。 <!-- rumdl-disable-line MD089 -->
入力ファイルが書き換えられることはありません。

lint のために、残った入力のすべての CRLF ペアが LF に変換され、末尾の LF があれば最大 1 つ取り除かれます。
単独の CR は正規化されず、禁止された制御文字として検査されます。コメントと scissors のフィルタリングを除き、
CLI はトリミング、Git のクリーンアップ、Unicode の正規化を行いません。特にフィルタリングは空行を追加せず、
残った空行を空白のクリーンアップとして削除することもありません。

セクションのルールにおける**空行**とは文字数がゼロの行です。スペースやその他の空白文字を含む行は空行ではありません。
Header、Body、Footer、および区切りは、残った論理行から決定されます。残った最初の行は、空であっても Header です。
診断には元の入力における 1 始まりの行番号が保持されます。
例えば、Header と Body の間のコメントは必要な空行の区切りにはならず、
区切りが欠けている場合は元の Body の行に報告されます。すべての行が除外された場合は空の Header として扱われます。
`header-format` が有効なら、フィルタリングによってメッセージが空になったことが元の 1 行目に報告されます。
その Rule が無効なら、そのような診断は出力されません。
通常の空の入力は、フィルタリングによって空になった入力とは区別されます。

## Header

Rule を適用する前に、リンターは最初の Header を設定された[無視パターン](configuration.ja.md#無視するメッセージ)と照合します。 <!-- rumdl-disable-line MD089 -->
一致するとメッセージ全体が通知なしに除外されます。以下の検査は無視されなかったメッセージにのみ適用されます。

解析可能な Header は次の形式です。

```text
<type>[(<scope>)][!]: <subject>
```

角括弧は省略可能な部分を表し、文字そのものではありません。パーサーは次の制約を適用します。

- Type は ASCII 英字で始まり、それ以降は ASCII 英字、数字、または `-` を使用できます。
- Scope がある場合は空でなく、Unicode 空白文字と `(` を含められません。最初の `)` で閉じられます。
  Scope には Unicode やその他の空白でない文字を含められます。
- Type または閉じ `)` の後に任意の `!` が続きます。パーサーはそれ以外にその意味を検査せず、
  `BREAKING CHANGE` Trailer も要求しません。
- 区切りはコロンに続く 1 つの ASCII スペースに限られます。Subject は空でも構いませんが、さらに別の ASCII スペースで
  始めることはできません。非 ASCII 空白文字を含むその他の文字は、Header パーサー自体では拒否されません。

解析に成功した Header では、各要素の Rule が、Type が設定されたリストに ASCII の大文字・小文字を区別しない比較で含まれること
（`type-enum`）、ASCII 大文字を含まないこと（`type-case`）、必要な場合に Scope が存在すること（`scope-required`）、
存在する Scope が許可された Scope に大文字・小文字を区別して完全一致すること（`scope-enum`）を検査します。
また、Subject が空でないこと（`subject-empty`）と、
リテラルの ASCII ピリオドで終わらないこと（`subject-full-stop`）も検査します。
Scope の Rule はデフォルトでは無効です。有効化の方法は設定リファレンスを参照してください。

`header-trim` は Header 全体の先頭または末尾の Unicode 空白文字を検査し、`header-max-width` は Header 全体の幅を測定します。
これらの検査と `control-character` は Header を解析できない場合も実行されます。解析に失敗した場合、
`header-format` が有効なら報告され、各要素の Rule は `header-format` が無効でも実行されません。
他の行は引き続き検査されます。

例えば、`FIX:bad.` は `header-format` に違反しますが、`type-case` や `subject-full-stop` は報告されません。
`feat: ` は空の Subject として解析されるため、デフォルト設定では `subject-empty` と `header-trim` の両方が報告されます。
`feat:  change` は 2 つ目の ASCII スペースのため `header-format` に違反します。

## セクションと区切り

Header の後で、リンターは最初の空でない行を探します。存在する場合、それは 3 番目の論理行でなければなりません。
すなわち、Header との間にはちょうど 1 つの空行が必要です。そうでなければ、その最初の空でない行に
`section-separator` が報告されます。Header の後に空でない行がなければ、Header の後に複数の空行があっても、
セクションの区切りは要求も検査もされません。

最初の空でない行とそれ以降のすべての行は、以下のヒューリスティックによって Body または Footer に分類されます。
Footer が最初の空でない行より後から始まる場合、その直前の連続する空行はちょうど 1 行でなければなりません。
そうでなければ、Footer の最初の行に `section-separator` が報告されます。Footer が最初の空でない行から始まる場合は、
Body と Footer の間の区切りを別途検査しません。メッセージ末尾の空行は、これらのセクション検査では要求も制限もされません。

## Footer と Trailer の検出

リンターは Header の後の最初の空でない行から走査し、次のいずれかに該当する最初の行を選びます。

1. 有効な Trailer。Body の行の直後を含め、走査中のどこにあっても該当します。
2. Trailer 候補で、Header の後の最初の空でない行、または空行の直後の行。

その行から Footer が始まり、それ以降のすべての行は Footer に属します。それより前の行は Body です。
該当する行がなければ、Header の後の内容はすべて Body です。この分類は `trailer-format`、`section-separator`、
および幅の Rule が有効かどうかとは無関係です。

Trailer を認識するために、リンターはまずトークンとその直後のテキストを特定します。

- 行が大文字・小文字を区別して正確に `BREAKING CHANGE` というテキストで始まる場合、その直後にさらにトークンらしい文字が
  続いていても、そのプレフィックス全体がトークンになります。
- それ以外の場合、最初の Unicode 空白文字、`:`、または `#` より前にある、空でない先頭の連続した文字列がトークンです。
  Unicode や句読文字を含めることができ、ASCII 英字やハイフンには限定されません。

**有効な Trailer** は、トークンの直後に `: `（コロンと 1 つの ASCII スペース）または ` #`（1 つの ASCII スペースと
ハッシュ）があり、その後に Unicode 空白文字をトリミングしても空でない値が続きます。値には追加のスペースやその他の文字を
含めることができます。例には `Refs: issue 123`、`Refs #123`、`レビュー: 完了`、`BREAKING CHANGE: reason` があります。

**Trailer 候補**は、空でないトークンの直後に `:` または `#` が続くか、1 つ以上の ASCII スペースの後に `:` または `#` が
続くものです。有効な区切りや値は必要ありません。例えば、`Refs:#123`、`Refs#123`、`Refs : value`、`Refs: ` は
候補ですが、有効な Trailer ではありません。
トークンと区切り文字の間に ASCII スペース以外の空白文字があっても候補にはなりません。
特別な `BREAKING CHANGE` プレフィックスは大文字・小文字を区別します。例えば `BREAKING CHANGELOG: value` は、
プレフィックスの後のテキストが区切り文字ではなく `LOG` で始まるため、Trailer として認識されません。

Footer の最初の行が無効な候補の場合、その行に `trailer-format` が報告されます。
それ以降の行は有効な Trailer である必要はなく、
有効な Trailer が現れる前であっても、継続テキスト、空行、不正な Trailer らしい行で構いません。
それらの行にも、適用される幅、末尾の空白、制御文字の検査は行われます。特に次の例を考えます。

```text
feat: change

Body text
Refs:#123
```

ここでは `Refs:#123` は空でない Body の行の直後にある無効な候補なので、Body のままです。これを `Refs: value` に
置き換えると、そこから Footer が始まり、Body と Footer の間の区切りがないことが報告されます。代わりに `Refs:#123` の前に
空行を挿入すると、Footer が始まり、`trailer-format` が報告されます。Footer が始まった後は、後続の `Refs:#123` であっても
Trailer として個別には検証されません。

## 空白と制御文字

`line-trailing-whitespace` は Header より後のすべての行について、空白のみの行を含め、末尾の Unicode 空白文字を検査します。
Header には代わりに `header-trim` が使われます。1 行に空白の診断と制御文字の診断の両方が出ることがあります。

`control-character` はすべての行について、C0 制御文字 `U+0000`–`U+001F`、DEL および C1 制御文字 `U+007F`–`U+009F`、
双方向書式制御文字 `U+202A`–`U+202E`、双方向分離制御文字 `U+2066`–`U+2069` を検査します。
タブと単独の CR も含まれます。LF の行区切り、および CRLF の一部として消費された CR は、検査対象の行には存在しません。
1 行に複数の禁止文字があっても、この Rule の報告は行ごとに最大 1 回です。

## 表示幅と診断

幅の Rule は、Unicode 17.0.0 のデータを使用する `unicode-width` 0.2.2 の文字列アルゴリズムにより、
各行全体を Display Columns で測定します。バイト数、Unicode スカラー値の数、書記素の数ではありません。
例えば`あ`は 2 カラムです。 <!-- rumdl-disable-line MD089 -->
幅が曖昧な文字はデフォルトで 1 カラムとして扱われますが、設定で CJK 向けの計算を選択できます。
実際の端末の表示は異なることがあります。

デフォルトでは、Header の幅が 50 カラムを超えると警告、72 を超えるとエラーになり、Body と Footer の行が 72 カラムを超えると
エラーになります。幅が制限値と等しい場合は許容されます。各幅の Rule は、超過した最も高いしきい値の重要度を使用して、
行ごとに最大 1 件の診断を報告します。Footer の幅は有効な Trailer だけでなく、検出された Footer の開始位置から後のすべての行に
適用されます。Body の幅はそれより前の Body の行に適用されます。しきい値の上書きとその他の Rule のデフォルト値については
設定リファレンスを参照してください。

診断は行番号、次に Rule ID の順にソートされます。デフォルトでは、有効な幅以外の Rule はエラーを報告します。
警告は `--strict` を使用しない限り CLI を失敗させません。エラーは常に CLI を失敗させます。
Rule の有効化、無効化、重要度の変更については設定リファレンスを参照してください。
